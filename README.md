# README

生产环境最先进的110告警系统，核心设计理念已从“接警再派警”转向“接警即派警、数据先于语音”，依托融合通信、高精度定位与情指行一体化，实现秒级响应。以下从系统架构、硬件、软件及关键设计四个维度展开。

### 一、总体系统架构设计

采用“双中心+分布式接入”架构，确保高可用与低时延。核心逻辑是：报警呼入瞬间，系统同步完成定位、警力匹配与三方通话建立，而非等待接警员问询完毕。

架构分为四层：
1.  接入层：融合 PSTN、移动定位网关、12110 短信、APP/小程序及一键报警设备，统一转换为 SIP 协议流。
2.  核心调度层：部署软交换与指挥调度引擎，负责话权管理、组呼、圈选与派单逻辑。
3.  数据支撑层：集成 PGIS（警用地理信息）、警综平台、视频专网及大数据资源池。
4.  应用层：接警席、指挥席、移动作战终端及联动单位（119/120/12345）接口。

### 二、硬件系统设计

生产环境需满足 7×24 小时不间断运行及等保三级物理要求。

- 通信与调度硬件：
  - 融合通信网关：支持 PDT/DMR 专网与公网 PSTN 无缝桥接，具备回声消除与抗丢包能力。
  - 录音录像服务器：全量录制接处警音视频，采用双机热备，存储保留不少于 180 日（部分严苛场景需 1 年）。
- 坐席与外设：
  - 双屏接警台：主屏显示警单与地图，副屏调取视频监控与预案。配备专业抗噪耳麦与指向性麦克风。
- 定位与网络硬件：
  - 高精度定位网关：对接运营商基站定位与 AGPS 辅助数据，实现报警手机位置秒级解析（室内精度要求较高时需结合 Wi-Fi 指纹库）。
- 安全硬件：
  - 部署硬件密码机（HSM）与 SSL 卸载设备，保障警情数据与公民身份信息的传输存储加密。

### 三、软件系统设计

软件是“最先进”的体现，重点在于自动化与智能化，减少人工录入。

- 极速派警引擎（核心创新）：
  摒弃传统“接听-记录-查询-派单”串行流程。当电话接入时，系统自动根据定位圈选半径 500 米内的在线警力，自动将报警人、接警员、最近警员拉入三方通话。民警在通话中直接问询并出动，实现“10 秒派警、60 秒到场”。
- 智能语音与语义辅助：
  实时将通话语音转写为文字，利用 NLP 自动提取“人、事、地、物”关键要素填入警单。同时识别敏感词（如“爆炸”“砍人”）并自动升级警情等级、触发红屏预警与领导短信通报。
- 可视化指挥与预案联动：
  基于 PGIS 实现“一张图”作战。接警瞬间，自动调取报警点周边 500 米内的视频监控（一屏显示 4-16 路）、卡口数据及历史警情。若触发“校园暴力”或“抢劫”预案，自动推送处置指引至出警民警警务通，并同步开启周边卡口布控。
- 情指行一体化协同：
  对于重大警情，系统支持“一键建群”，将刑侦、网安、交警及属地分局拉入作战群，共享位置与视频，实现扁平化指挥，避免层层转达。

### 四、关键设计考量（系统设计题得分点）

- 高可用性：核心调度服务器采用双活集群，切换时间小于 3 秒；网络采用双路由冗余，确保单点故障不影响接警。
- 安全合规：严格遵循等保三级与密码应用要求。接警席操作需双因子认证，警单修改留痕不可篡改，敏感数据（如报警人手机号）在数据库内加密存储。
- 排队与防拥堵：设计溢流机制。当 120 坐席全忙时，自动语音提示并引导至短信/APP 报警；若遭遇恶意呼入，自动识别并拉入黑名单，保障生命线畅通。

此方案兼顾了前沿的“极速派警”理念与生产环境的稳定性要求，适合作为系统设计题的核心框架。

### 需不需要MQ：需要，但定位要准

110系统的MQ承担两类职责，不能混为一谈：
* 警情数据流：接处警数据向省厅/部级汇聚平台实时推送。公开的采购文件明确要求接处警系统通过Kafka消息队列推送电话呼入、受理单、反馈单等数据，替代传统ETL抽取，实现无时延传输。
* 内部事件驱动：派警引擎触发后，异步通知PGIS圈选、视频调取、短信通知、警务通推送等下游服务。这些动作彼此独立，用MQ广播事件最合适。

但核心调度信令（如SIP呼叫控制、话权管理）不应走MQ，应走软交换/CTI的专用信令通道。MQ只处理“派警成功后通知谁”这类业务事件，不处理“通话怎么接续”。

### 技术选型：Kafka为主，RabbitMQ为辅（或按场景二选一）

在110生产环境中，选型取决于你更看重吞吐与数据汇聚还是灵活路由与任务重试：

首选 Kafka 的场景（数据汇聚与广播）
如果系统需要向省厅/部级平台实时汇聚警情数据，或需要将警情事件广播给多个下游分析模块，Kafka是更稳妥的选择。公安采购文件中已明确出现“基于Kafka消息队列的数据传输程序”用于接处警数据汇聚。它的分区有序性可保证同一警单的多次状态变更按序处理，高吞吐特性也足以应对重大警情期间的事件洪峰。

考虑 RabbitMQ 的场景（内部任务队列与复杂路由）
如果需要在系统内部做精细化的任务分发——比如根据警情类型（刑事/治安/求助）路由到不同处置队列，或需要对派警失败的通知任务做延迟重试（如民警终端离线时，30秒后自动重发），RabbitMQ的原生延迟队列和死信队列机制更省事。它的单机吞吐虽低于Kafka，但110坐席规模（通常百级）的内部事件量级完全够用。

结论：若只能选一个，选Kafka，因为警情数据汇聚是硬性合规要求，且公安领域已有明确用例。内部任务重试逻辑可在应用层用数据库+定时任务兜底。

### 自研还是开源：开源打底，自研封装

不要自研MQ内核。 110系统是7×24生命线工程，自研消息中间件意味着你要自己解决分布式一致性、副本同步、故障转移、消息不丢不重——这是数年积累的坑，不值得在接警系统上从头踩。

推荐策略：开源中间件 + 自研“警情消息网关”
* 底层：直接采用 Kafka（或 RabbitMQ）开源版，利用成熟社区和运维工具。
* 自研层：在MQ之上封装一个警情消息规范层。核心工作包括：定义统一的警情事件 Schema（警单ID、类型、优先级、目标系统）；实现生产端幂等（同一警单不重复派发）；实现消费端幂等（下游服务按警单ID去重，防止网络重试导致重复通知）；增加消息轨迹追踪（每一条派警通知可追溯“何时发出、谁消费、是否成功”），用于故障定责。

这一层代码量不大，但能把你和开源MQ的耦合隔离开，未来若需替换底层或做国产化适配（如对接国产消息中间件），改动范围可控。

安全合规提醒：若项目有国产化要求，Kafka/RabbitMQ本身是开源软件，合规风险较低，但部署的操作系统与数据库需选用国产产品。消息内容中的报警人手机号、地址等敏感字段，应在生产端加密后再入队，而非依赖MQ自身的安全机制。
