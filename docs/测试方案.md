# 测试方案

## 1. 范围与目标

本文描述 Advanced110AlarmSystem 首版 Java 实现（Maven 多模块）的测试策略、用例与执行方法，并映射[概要设计](概要设计文档.md)第 8 节验收场景。当前仓库执行的验证为本地/CI 可重复的自动化测试；性能压测、真实线路与容灾演练不在本版范围（见第 7 节未覆盖项）。

被测工程：`alarm-server`（Spring Boot 入口）+ `alarm-contracts/alarm-domain/alarm-application/alarm-infrastructure`。测试依赖 H2 内存库，可离线独立运行，CI 无需外部中间件。

## 2. 测试分层与目标比例

| 层级 | 位置 | 目标 | 当前用例 |
| --- | --- | --- | --- |
| L1 领域单元测试 | `alarm-domain/src/test` | 状态机所有合法/非法迁移、终态判定、地理距离语义 | `DispatchStateMachineTest`、`IncidentStateMachineTest`、`GeoUtilsTest` 共 12 例 |
| L2 端到端集成测试 | `alarm-server/src/test` | REST 全链路业务闭环 + 幂等/并发/超时/冲突边界 | `AlarmSystemFlowTest` 共 12 例 |
| L3 构建验证 | Maven `verify` | 全模块编译、测试、Spring Boot 可执行 jar 打包 | CI 工作流 |
| L4 手工冒烟 | `mvn spring-boot:run` + curl | 首启健康检查与样例请求 | 见第 5 节脚本 |

策略：领域规则（纯函数）下沉 L1 以获得全覆盖；业务边界（幂等键、乐观锁、超时、并发预占）在 L2 以真实 HTTP + 真实事务 + 真实约束（唯一键）验证；不使用 mock 领域规则，只替换时钟为可推进的测试实现。

## 3. L2 端到端用例清单（AlarmSystemFlowTest，@Order 顺序执行）

| # | 用例 | 验证点 | 预期 |
| --- | --- | --- | --- |
| 1 | registerIncident_idempotentAgainstDuplicateSource | (channel,sourceId) 唯一约束防重复建单；同 Idempotency-Key 同请求返回缓存；同键不同请求体 409 ALM-2102 | 201→201(同 id)→201(缓存)→409 |
| 2 | missingOperatorHeaderReturns401 | 缺 X-Operator-Id → 401 ALM-1101 | 401 |
| 3 | verifyRequiresAddress_thenAccepts | VERIFY 缺 verifiedAddress → 422 ALM-1005；补齐后 PENDING_VERIFICATION→ACCEPTED，版本 0→1 | 422→200 |
| 4 | staleVersionUpdateConflict409 | expectedVersion 过期 → 409 ALM-1002 | 409 |
| 5 | upsertUnits_nearHasCapacityForSingleReserve | 警力 upsert 正常；availability=20 保证并发预占竞争恰好一次成功 | 200 |
| 6 | recommendationOnlyWithinRadius | 500 米圈选仅含近端警力（球面距离计算） | 仅 U-NEAR |
| 7 | concurrentDispatch_onlyOneReserveSucceeds | 两线程并发对同一警力派遣：条件 UPDATE(`availability>=20`) 原子预占，恰好 1 个 201、1 个 409 | 201×1, 409×1 |
| 8 | sameIdempotencyKeyReturnsCachedResult | 同键同请求重复提交派遣不新增任务；取消派遣 CANCELLED 并释放额度 | 201×2 同体, 200 |
| 9 | receiptChain_reachesFeedbackDone_andIncidentPendingReview | 回执链 ACCEPTED→ENROUTE→ARRIVED→FEEDBACK_DONE；同 commandId 幂等重放不推进；全终态后警单自动 DISPATCHING→PENDING_REVIEW | 200 链 + PENDING_REVIEW |
| 10 | closeRequiresConclusion_thenClosedAndIdempotent | 结案缺结论 → 422；结案成功 CLOSED v5；同键重放返回缓存 | 422→200→200 |
| 11 | reopenAndAuditTrail | REOPEN CLOSED→PENDING_REVIEW；审计记录按目标可查、首条为 INCIDNET_CREATED | 200 |
| 12 | timeoutScanMarksExpiredAndLateAcceptRejected | 时钟快进 40s 后扫描将 PENDING_CONFIRM→TIMEOUT；TIMEOUT 后迟到接单被拒（409 ALM-1003，不能激活过期任务）；全终态自动待复核 | ≥1, 409, PENDING_REVIEW |
| 13 | r02_sameIdempotencyKeyOnDifferentIncidentsMustNotReplayOtherResult | 评审缺陷回归 R02：同一操作人用相同幂等键核实不同警单，第二次必须作用于目标对象本身，不得重放第一条的缓存结果 | 200 且 incidentId 正确 |
| 14 | r04_telemetryUpssertCannotRaiseAvailabilityDuringActiveReservation | 评审缺陷回归 R04：活动预占期间(avail=0)遥测 upsert 抬升额度 → 422（防绕过原子预占）；不抬升的遥测照常允许 | 422→200(不抬升) |
| 15 | r05_receiptCannotSelfDeclareTimeout | 评审缺陷回归 R05：终端回执禁止自声明 TIMEOUT（TIMEOUT_BY_SYSTEM_ONLY，409）；系统扫描仍可将过期任务置 TIMEOUT | 409 then ≥1 |
| 16 | r03_dispatchStatusChangedEventCarriesPostCasVersion | 评审缺陷回归 R03：DispatchStatusChanged 的 aggregateVersion 必须等于 CAS 后的 DB 版本（ops/events 接口核对），修复前事件中 v=0 与 DB v=1 不一致 | 事件 v == 回执响应 v |

## 4. L1 领域用例要点

- `IncidentStateMachine`：待核实仅允许受理/撤销；已不允许“未受理先派遣”；CLOSED 仅可 REOPEN 至 PENDING_REVIEW；同状态保持不算迁移。
- `DispatchStateMachine`：PENDING_CONFIRM 禁止跨级跳到 ENROUTE；TIMEOUT 之后不可 ACCEPTED；终态集合 FEEDBACK_DONE/REJECTED/TIMEOUT/CANCELLED 与 ACTIVE 判定互补。
- `GeoUtils`：零距离、纬度 1°≈111km、微量经度差在百米量级（半径圈选语义）。

## 5. 本地执行方法

```bash
# 全量（编译 + 单元 + 集成 + 打包）
mvn -B verify

# 仅领域单元测试
mvn -B -pl alarm-domain test

# 仅端到端集成测试
mvn -B -pl alarm-server test

# 手工冒烟：启动后依次执行
mvn -B -pl alarm-server spring-boot:run
# 1) 登记警单（201）
curl -s -X POST http://localhost:8080/api/v1/incidents \
  -H "Content-Type: application/json" -H "X-Operator-Id: OPER-01" -H "Idempotency-Key: smoke-1" \
  -d '{"channel":"PHONE","sourceId":"SMOKE-1","priority":"HIGH","type":"ROBBERY","description":"smoke","location":{"x":116.39,"y":39.9,"source":"CELL","observedAt":"2026-10-29T02:00:00Z"}}'
# 2) 登记/更新警力（200）→ 核实（PATCH VERIFY）→ 派遣 → Outbox 手动补发 /ops/outbox/run
```

判定标准：CI 中 `mvn -B verify` 退出码 0 且无 failed/error 用例；任何失败须修复或经评审降级为已知问题并记录 issue。

## 6. 与验收场景的映射（概要设计第 8 节）

| 验收场景 | 覆盖用例 |
| --- | --- |
| 重复呼入事件不会重复建单 | #1 |
| 同一派遣请求重试不会新增任务 | #8（幂等键缓存）、#9（commandId 回执幂等） |
| 并发派遣遵守警力预约规则 | #7 |
| 数据库提交后进程崩溃仍可补发事件 | Outbox 与业务同事务（实现保证）；补发验证由 #运行 outbox/run 参数与 L2 事务提交语义间接覆盖，进程级崩溃注入属 L4/后续项 |
| 重复和乱序消费不会回退状态 | #9 幂等重放不推进；乱序行为依赖 aggregateVersion 检测，消费者为规划中 Kafka 适配，暂未覆盖 |
| 超时、迟到回执可追踪 | #12 超时标记 + 迟到接单拒绝 |
| 事件版本一致性（R03） | #16 + `scripts/review-probes.py` 重放证据（docs/evidence） |
| 权限越界被拒绝并留痕 | #2（401）；授权矩阵（403）为规划项 |
| 人工锁定地址不被异步定位覆盖 | 实现层面 verifiedAddress 与 location 分列保存；无异步定位组件，回归由 #3 保障 |

## 7. 未覆盖项与后续计划

1. **契约/Schema 演进测试**：事件 payload 兼容性（增加可选字段、v2 版本窗口）待引入 schema registry 后测试。
2. **故障注入**：Kafka 中断、数据库主备切换、中心切换演练 → 依赖真实中间件环境（Testcontainers + Kafka 计划中）。
3. **性能验收**：按部署文档第 7 节，以真实容量模型执行 P95/P99 计时，指标冻结由业务确认。
4. **安全测试**：双因子认证、敏感字段加密存储、日志脱敏 → 接入真实 IDP 与密钥管理后补充。
5. **审计防篡改归档**、录音证据链、备份恢复演练 → 部署文档相关章节承接。

## 8. CI 执行说明

`.github/workflows/ci.yml` 在 push/PR 时执行：

1. Temurin JDK 17 + Maven 缓存；
2. `mvn -B -V verify` 全量校验与打包；
3. 归档 `**/surefire-reports/*.xml` 便于失败定位（可从 Actions 运行详情下载）。

任何一次运行以 `gh run view <run-id> --log-failed` 查看失败日志，修复后重跑，以一次成功的 run 作为构建证据（部署文档第 4 节要求）。
