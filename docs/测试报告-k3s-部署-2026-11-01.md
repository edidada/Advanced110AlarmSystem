## 二、middleware 复用方式（本次改造核心）

应用此前为 H2 内存库 + 日志模拟总线，为了 k3s 部署并按"redis 用 middleware 的 redis、其他类似"的原则做了适配（commit `33c67bc`）：

| 依赖 | 本地/单测（默认 profile） | k3s（k8s profile） | 改造点 |
|---|---|---|---|
| 关系库 | H2 内存库（`schema.sql`） | `mysql.middleware.svc.cluster.local:3306/alarm110`（`schema-mysql.sql`） | 新增 MySQL 8 方言 DDL：`CLOB→MEDIUMTEXT`、`TIMESTAMP→DATETIME(3)`（避开通 MySQL 的隐式 DEFAULT/ON UPDATE）、`"key"` 改名 `idempotency_key`（MySQL 保留字，H2/MySQL 同步迁移） |
| 缓存 | 无 | `redis.middleware.svc.cluster.local:6379`（带密码，来自 middleware/redis-secret 同源 secret） | 新增 Redis 读缓存：仅缓存 `POST /incidents/recommendations-preview`（advisory 只读，TTL 15s），JSON 序列化（record + Instant 兼容）；强一致写路径全部直查 MySQL |
| 事件总线 | 日志（`alarm.event-bus.type=log`，默认） | Kafka（`alarm.event-bus.type=kafka`，`KafkaEventPublisher`） | 落地设计预留的 Kafka 适配位：key=incidentId（同警单事件保序进同分区）、payload 即 Outbox 信封 JSON、同步等待确认、失败由 OutboxRelay 留 PENDING 补发（至少一次语义不变） |

**探针分组设计**（吸收 galaxy-mall order 聚合健康误摘 Pod 的教训）：liveness 只含进程自身；readiness 含 `readinessState,diskSpace,db`——故意**排除 redis/kafka**：读缓存有 TTL 降级、事件有 PENDING 补发，两者抖动时应用仍能正确服务，不应摘除流量；MySQL 是强依赖所以纳入。

幂等/并发约束未因部署改变：幂等键作用域仍是"操作人+操作+目标对象 id"（R02）、事件聚合版本仍用 CAS 后新值（R03）、预占期间遥测 upsert 仍拒绝抬升额度（R04）、终端不得自声明 TIMEOUT（R05）——四项回归在下文 k3s 实测中全部复验通过。

## 四、中间件复用的集群侧证据

### 4.1 MySQL（middleware/mysql）

```sql
-- kubectl exec mysql -- mysql ... alarm110
incidents=3, dispatches=3, outbox_total=20, outbox_published=20, idempotency=17, audits=17
```
6 张表全部由应用首启自动建出（`spring.sql.init`，MySQL 方言脚本一次通过；副本滚动重复执行由 `continue-on-error` 按"索引已存在"跳过）。

**持久化回归**：删除 worker3 上的 Pod → Deployment 重建 → 重建前后 `GET /incidents/{id}` 响应**逐字节一致**（CLOSED v4 + 2 条任务），
证明 H2 内存库已被现网 MySQL 持久化真正替代（证据：`docs/evidence/2026-11-01/incident-before-restart.json` / `incident-after-restart.json`）。

### 4.2 Kafka（middleware/kafka）

主题 `alarm.bus.events`（3 分区，broker 广播地址即 svc DNS，Pod 内客户端无需额外 hosts）：

```
alarm.bus.events:0:41  partition=1:32  partition=2:27   （合计 100 条）
```

抽样消费到的消息与 Outbox 信封完全一致（`IncidentCreated`，aggregateVersion=0，payload 内嵌业务字段）——
验证了事件从本地落库（事务内写 outbox_event）→ 定时/手动补发 → Kafka 投递 → key=incidentId 三分区散列的完整链路，
且 outbox 表 20/20 处于 PUBLISHED、无 PENDING 积压。

### 4.3 Redis（middleware/redis）

预览接口调用后立即在 redis Pod 内扫到缓存键（record 作默认键，TTL 15s）：

```
recommendation-preview::RecommendationPreviewRequest[incidentId=cba1d379-…, location=null, radiusMeters=500]
```

即读缓存写在跨副本共享的现网 Redis 上；测试用例中特意用不同 radius 键位绕开缓存来验证预占扣减的实时性（T11）。

| 问题 | 定位 | 处理 |

## 七、限制与后续建议

1. **Redis 缓存经纬度键**：`recommendation-preview` 当前用 record 全文做键（含 observedAt），遥测更新后自然产生新键，旧键靠 TTL 清理；若预览 QPS 上量，建议改显式键（incidentId/radius/坐标网格）缩短键长。
2. **schema 初始化依赖 `continue-on-error`**：MySQL 8 无 `CREATE INDEX IF NOT EXISTS`，重复初始化按报错跳过；若未来引入 Flyway/Liquibase，可去掉这个宽容开关。
3. **Kafka 单 broker**：`alarm.bus.events` replication.factor=1，broker 重建不可用期间 OutboxRelay 会保留 PENDING 并限速补发（链路语义正确，但有积压窗口）；对齐现网 `num.partitions=1` 的集群现状，暂不扩。
4. **CI 与集群仍分离**：GitHub Actions 托管 runner 进不了内网 registry/集群（见 runbook 第 7 节），本次镜像是本地 Docker 构建 + 推送；后续如需 CI 自动部署，走 VM107 self-hosted runner 或 GitLab CE 路线。
5. **副本数 2 + maxUnavailable=0** 已可滚动发布；若做无感发版，补 `PDB`（零停机文档 zero-downtime.md 的建议仍然适用）。
