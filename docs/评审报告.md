## 1. 评审结论

当前工程可作为接处警业务原型继续迭代，不具备生产上线条件。模块分层、事务内 Outbox、条件预约和基本状态机已落地，但认证授权、持久化生产适配、真实消息投递、容灾与监控尚未闭环。24 项既有测试通过不能证明设计全部实现，也不能消除本次实际复现的问题。

优先修复幂等目标隔离、派遣事件版本和预约额度覆盖，再完善安全、消息链路及生产数据库。数据库硬件规格和性能 SLO 参见[数据库硬件容量规划](数据库硬件容量规划.md)、[系统监控与性能指标](系统监控与性能指标.md)，其中数字均为待验证的规划值。

## 3. 发现清单

严重度定义：P0 为生产接入阻断项；P1 为业务正确性或可靠性严重问题；P2 为规模、运维、契约与测试质量问题。已声明的原型缺口同样计入上线门槛，不暗示实现曾承诺生产就绪。

### R01 / P0：请求头模拟身份，无角色和对象级授权

依据：`alarm-server/.../web/WebSupport.java:26` 接受任意非空 X-Operator-Id；UnitController 中审计读取、警力更新与 Outbox 操作只有该检查，DispatchController 超时扫描同样如此。无真实身份校验及辖区/终端归属校验。详细设计已声明模拟认证，但不能接入真实警情。

影响：能访问 HTTP 服务的调用方可自称任意操作人，读取警单审计、更新警力或触发管理操作。修复：接入可信身份源，覆盖角色、辖区、对象与终端归属授权；隔离运维入口，审计拒绝操作。验收：伪造身份 401、跨辖区与跨终端 403、管理操作权限矩阵通过。

### R02 / P1：警单修改与结案幂等范围未包含目标 ID（已复现）

依据：`alarm-application/.../service/IncidentService.java:120,211` 的 scope 仅含操作人和操作，摘要只计算请求体。相同操作人使用同键、同体修改两个不同警单时，第二个请求返回第一个警单缓存结果，实际未修改第二个警单。结案存在同类路径，尚未单独动态复现。

复现：创建 A/B，使用同一键和相同 VERIFY 请求依次受理，第二次 HTTP 200 的 incidentId 为 A，查询 B 仍为 PENDING_VERIFICATION。修复：在 scope 或请求摘要中纳入规范化资源标识和操作类型；清理或迁移旧缓存策略。验收：相同目标幂等，不同目标不会命中其他警单结果。

### R03 / P1：派遣状态变更事件携带旧版本（已复现）

依据：`DispatchService.java:207-213,234-239,251-268`。CAS 保存 updated 副本后，后续事件仍读取旧 task.version；回执和超时仅修改旧对象 status，取消甚至保持旧对象。事件 `aggregateVersion` 因而落后一个版本。

复现：任务从版本 0 变更为 TIMEOUT，接口返回 version=1，DispatchStatusChanged 信封却为 aggregateVersion=0。创建事件也为版本 0，下游按版本去重可能丢弃后续状态。修复：统一使用成功持久化后的对象产生事件，核对回执、取消、超时全部路径。验收：数据库版本与信封一致、同一任务严格推进；不要只检查 HTTP 响应版本。

### R04 / P1：警力上报可以覆盖活动任务的预占额度（已复现）

依据：`UnitService.java:133` 使用请求 availability 替换现值；`UnitStatusRepositoryImpl.java:84` 通过减 20 预约。已有任务预占后，同一警力上报旧 availability 可把剩余额度恢复，乐观锁只能防同一瞬间并发，不能阻止顺序覆盖。

复现：availability=20 的警力被 A 预约后再次上报 20，B 仍成功派遣（201），A 的任务仍活动。修复：拆分上报基础能力与预约占用，以持久化预约记录计算剩余容量；明确“一警力多任务”的批准规则。验收：心跳、乱序上报、重试均不能增加被占用额度；不同警单并发竞争仍遵守容量。

### R05 / P1：回执接口允许终端设置系统超时或取消（已复现）

依据：`DispatchService.java:198-199` 直接将 targetStatus 交给通用状态机；状态机允许 PENDING_CONFIRM→TIMEOUT/CANCELLED。详细设计 5.5 仅允许 ACCEPTED/REJECTED/ENROUTE/ARRIVED/FEEDBACK_DONE，但服务未限制入口允许值。

复现：未到 deadline 的任务通过 receipts 提交 TIMEOUT，HTTP 200、版本推进并释放额度。修复：将终端回执白名单与系统超时、指挥取消入口隔离；结合终端身份和任务归属检查。验收：终端 TIMEOUT/CANCELLED 请求失败，合法超时扫描和有权取消仍有效。

### R06 / P1：Outbox 未提供有序可靠消费闭环

依据：`OutboxRelay.java:38-50` 扫描后直接 publish，失败 continue；`OutboxRepositoryImpl.java:53` 仅按 created_at 排序，没有领取租约/互斥与稳定次序；多个实例及手动扫描可并行处理同一批。单条失败后继续后续事件还会造成同聚合越序。

至少一次语义允许重复，但当前没有消费去重实现与版本缺口补偿；LogEventPublisher 只记日志即标 PUBLISHED，无法证明 Kafka 或终端收到。默认批量 100、fixedDelay 5 秒，在发布耗时为零时单定时器上限约 20 条/秒；实际更低，多实例又引入重复，不能用加实例替代领取设计。

修复：真实发布确认、按聚合有序领取、稳定排序、持久化重试/隔离及消费端去重；记录异常和年龄指标。验收：双实例、单条毒消息、发布后标记前崩溃、Kafka 断连与恢复、同聚合越序补偿。该项为静态确认的能力缺口，未做真实 Kafka 故障实验。

### R07 / P0：生产持久化、恢复和数据库适配缺失

依据：`alarm-server/src/main/resources/application.yml:6-12` 默认 H2 内存库、固定 org.h2.Driver、空密码、启动自动 schema 初始化。只改 URL 不能完成生产数据库切换。无版本化迁移、备份恢复和中心切换实现。

修复：生产 profile 强制外部凭据与匹配驱动、禁用演示默认值；版本化迁移并实测目标数据库 SQL、唯一键冲突后的事务行为、索引和时间类型。验收：持久化重启、迁移升级/旧版兼容、隔离环境 PITR 与切换演练。采购更强服务器不会解决这些问题。

### R08 / P2：并发用例把所有失败都计为冲突，且不足以证明唯一预约

依据：`AlarmSystemFlowTest.java:226-229`，任意非 201 响应及异常都增加 conflict，未断言 409/错误码，也未回查数据库副作用。两请求还使用同一警单版本，即使警力预约错误，警单 CAS 也可能让一个请求失败。因此文档“201×1、409×1”和警力唯一预约的断言强度高于实际代码。

修复：捕获每个 Future 结果，精确断言 HTTP 409 与业务码；不同警单竞争同一警力；核对任务数、额度、事件和回滚。集成测试拆分独立 fixture，减少 @Order 共享状态造成的级联失败。

### R09 / P2：输入与错误处理、安全观测不完整

依据：`GlobalExceptionHandler.java:70-73,93` 将 IllegalStateException 当 400，截断异常消息后返回客户端；截断不等于脱敏，内部序列化故障也不应算参数错误。Incident 修改未复用创建校验；UnitService 未完整校验坐标范围、source 与未来时间，推荐读取 listAll 全表再计算距离。

修复：统一 DTO/业务长度与地理校验，内部错误返回安全 500；错误日志字段化脱敏；按辖区与空间索引查询并限制候选数。验收：超长值、缺枚举、非法经纬度、未来/过期定位、内部异常与大规模推荐测试。

### R10 / P2：超时扫描与监控尚未自动闭环

依据：定时器只有 OutboxRelayScheduler，派遣超时仅提供 `/ops/dispatch-timeout/run`；不调用接口则任务一直占用额度。未引入 Actuator/Prometheus registry，oldestPendingAgeSeconds 只是方法，没有采集端点和告警规则。

修复：实现有批次和互斥的超时调度、任务心跳与逾期告警，补齐指标采集和告警接收。验收：无人工调用也能处理超时，调度停止可被监控发现；监控断采也必须报警。
