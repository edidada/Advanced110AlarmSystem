# 系统监控与性能指标

日期：2026-10-29；适用范围为目标生产系统及现有原型的差距治理。本文提出候选 SLI/SLO、采集和告警方案，数字为设计预算，不是已测结果或已签署 SLA。当前代码未接入 Actuator/Prometheus，CTI、Kafka、录音和真实终端尚未实现；以下指标名除明确说明外均为拟新增。

## 1. 监控架构与测量规则

应用通过 Micrometer/受控指标端点输出；主机、数据库和 Kafka 使用经过权限审查的 exporter；通信与媒体通过厂商接口采集；浏览器和终端测量用户体验；OpenTelemetry 传播 trace，日志集中采集，Prometheus 汇总，Grafana 展示，告警管理组件通知值班。监控服务和探针跨故障域，至少配置独立于业务中心的黑盒探测与告警出口。

指标标签只使用 environment、service、instance、route模板、statusClass、有限错误码及有限辖区。incidentId、dispatchId、eventId、电话号码、精确位置和原始 URL 不作为指标标签；使用脱敏日志/trace 关联，限制保留和访问。高基数会影响 Prometheus 性能。[Prometheus 官方实践](https://prometheus.io/docs/practices/the_zen/)

时间统一 UTC，节点时间偏差监测；跨系统端到端使用关联 ID 与可验证时间戳，本机时长用单调时钟。Histogram 配置覆盖目标阈值的桶，并聚合桶后计算 P95/P99，不平均各实例百分位。低流量时展示样本数，不把无数据解释为0延迟。[Histogram 官方说明](https://prometheus.io/docs/practices/histograms/)

## 2. 业务 SLI 与候选 SLO

| SLI | 测量起止/口径 | 候选目标 | 数据来源/责任 |
| --- | --- | --- | --- |
| 核心 API 可用率 | 合法受理/核实/派遣/回执请求中，未发生服务失败或超时的比例 | 每30日≥99.95% | 入口与应用双侧；后端/运维 |
| 建单耗时 | HTTP请求到达应用→业务与Outbox事务提交且响应完成 | P95≤300ms，P99≤800ms | 应用Histogram；后端 |
| 派遣提交耗时 | 有权派遣请求到达→任务/预约/Outbox提交且响应完成 | P95≤300ms，P99≤800ms | 应用与DB trace；后端 |
| 推荐耗时 | 有效查询到达→候选列表完成 | P95≤500ms，P99≤1s | 应用；算法/后端 |
| 回执登记耗时 | 有效回执到达→任务状态提交且响应完成 | P95≤200ms，P99≤500ms | 应用；后端 |
| 事件端到端延迟 | Outbox提交→下游业务副作用持久化确认 | P95≤2s，P99≤5s | 事件与消费端；集成 |
| 派遣通知送达率 | 在批准期限内收到终端送达确认的任务/应通知任务 | 候选≥99.9%，60秒窗 | 通知适配器，不以broker ACK替代；集成 |
| 呼叫接续成功率 | 厂商返回成功接续/有效测试或真实呼入尝试 | 按线路合同确定，暂不承诺数值 | CTI/CDR；通信负责人 |
| 呼叫接续时延 | 网关登记呼入→坐席媒体双向建立 | P95/P99，门槛按厂商验收 | 网关/媒体探针 |
| 录音完整率 | 可检索且长度/分段完整的已结束需录音通话/应录音通话 | 候选100%，缺片即调查 | 通话与存储对账；通信/存储 |
| 派遣业务响应时间 | 呼入登记→人工批准派遣→终端接单分段计时 | 展示分布，按辖区确认 | 业务事件；业务负责人 |
| 到场时长 | 接单/出发→到场，分别记录 | 统计与业务复盘，不设通用60秒软件SLA | 终端回执；业务负责人 |

可用率同时提供原始HTTP错误、业务拒绝与服务失败口径：合法409版本冲突不算服务不可用，但异常冲突率单独报警；鉴权/参数错误单独计数，内部错误误映射400不能被排除以美化SLO。超时、入口无法连接和维护中断计入用户视角；无请求期间用合成探针补充，测试写入仅到隔离测试租户/环境。

30日99.95%的时间口径预算为21.6分钟；请求口径预算为有效请求数×0.05%，二者分开报告。业务“10秒派警”需定义人工确认是否计入；当前5秒轮询Outbox并不满足稳定的2秒端到端目标，需要先改造调度与吞吐。

## 3. 指标目录和初始告警阈值

以下为预生产校准起点。P1需值班立即处置，P2进入运维处理；故障已导致接警中断时升级最高业务事件，不等待持续窗口。

| 范围 | 指标（拟定） | 初始阈值/窗口 | 动作与责任 |
| --- | --- | --- | --- |
| 业务入口 | `alarm_http_requests_total`、`alarm_http_duration_seconds` | 核心服务失败率>1%且5分钟≥100请求，持续5分钟；黑盒连续3次失败 | P1：查入口、应用和DB；运维 |
| 业务正确性 | 不合法状态、异常重复任务、预约余额不一致 | 确认任一一致性违规 | P1：暂停自动派警并对账；后端/业务 |
| 派遣 | `alarm_dispatch_pending_overdue`、接单/超时/拒绝率 | 最老待确认任务超过deadline+10秒，持续1分钟 | P1：检查扫描器与终端；调度/后端 |
| 定位 | 可用率、位置年龄、低精度占比 | 过期位置占比>10%，5分钟 | P2：定位适配与网络；集成 |
| 外部依赖 | 各受控接口超时率、熔断状态、耗时 | 超时>5%且≥20请求/5分钟 | P1或P2按是否阻断核心业务；集成 |
| Outbox | `alarm_outbox_pending`、`alarm_outbox_oldest_pending_age_seconds` | 最老>10秒持续2分钟为P2；>60秒持续1分钟为P1 | 查发布失败和容量，禁止盲目清空；后端 |
| 发布/重试 | 发布失败率、重试次数、隔离队列数 | 隔离事件>0或发布失败持续2分钟 | 按影响分级，确认后受控重放；集成 |
| 调度器 | 上次成功时间、轮询时长、处理数量 | 超时任务扫描距上次成功>2个周期+10秒 | P1：确认是否占用警力不释放；后端 |
| Kafka（待接入） | ISR、离线分区、未充分复制分区、消费lag时间 | 离线分区>0立即P1；副本不足持续1分钟；消费最老>30秒持续2分钟 | 查broker/网络/消费者；中间件 |
| JVM | CPU、heap、GC暂停、线程、进程重启 | heap>80%持续10分钟；GC P99>200ms持续5分钟；重启≥3次/10分钟 | P2，业务受损升P1；后端/运维 |
| 连接池 | active/max、pending、获取耗时 | 使用率>80%或获取P99>100ms持续5分钟 | 查事务、慢SQL和连接泄漏；后端/DBA |
| 数据库 | 事务提交时延、锁等待、死锁、慢SQL | 提交P99>20ms持续5分钟；阻塞>5秒；死锁>0需分析 | P2，核心写阻断升P1；DBA |
| DB复制 | WAL产生速率、回放字节差、确认水位、复制状态 | 连接断开持续30秒；异地有效回放年龄>30秒预警、>60秒告警 | DBA；结合RPO禁止不安全提升 |
| 数据库维护 | 长事务、dead tuples、vacuum/归档失败、复制槽保留量 | 长事务>60秒；归档连续失败；槽保留超过预算70% | P2：检查阻塞和磁盘增长；DBA |
| 磁盘 | 可用空间、IO延迟、队列、预计耗尽时间 | 使用>70%预警，>85%严重；预测<24小时耗尽P1 | 扩容/受控清理，禁止删除未归档事实；DBA/运维 |
| 主机/网络 | CPU、内存压力、swap、丢包、网络吞吐、时钟差 | CPU>70%持续10分钟；swap持续；时钟差>100ms | P2；关联请求尾延迟；运维 |
| SIP/RTP | 接续失败、活跃通话、线路容量、丢包/抖动/单通 | 容量>80%持续5分钟；丢包>1%持续1分钟候选 | 通信负责人按厂商与编解码器校准 |
| 录音/对象存储 | 缺片、写失败、检索失败、归档滞后、容量 | 完结通话超过归档宽限仍缺片>0；写失败持续1分钟 | P1：保存现场并按通话核对；通信/存储 |
| 安全 | 登录失败、越权、密钥错误、证书到期 | 异常峰值；证书<30日预警/<7日严重 | 安全负责人，告警不含警情正文 |
| 备份/恢复 | 最新成功备份年龄、WAL连续性、恢复演练年龄 | 日备份>26小时；归档缺口；演练超过批准周期 | P1/P2按RPO影响；DBA |
| 监控本身 | up、scrape失败、规则求值失败、告警心跳 | 断采>2分钟；独立告警心跳缺失>5分钟 | 运维；不能将断采看成业务恢复 |

DB回放时间差在无业务写入时可能误导，须结合生成LSN、水位与心跳事件判断；PostgreSQL统计视图可提供活动、IO和复制观测，具体字段按选定版本实现。[官方统计说明](https://www.postgresql.org/docs/current/monitoring-stats.html)

## 4. 采集、看板与告警运行规则

核心业务与基础设施每15秒采集，DB重查询/一致性对账每60秒或更低频；采集SQL设置超时并评估开销。示例保留原始指标30日、降采样趋势13月，最终按容量与审批确定；日志、trace、审计和录音使用各自留存策略。

四类看板：值班总览（接警、派遣、通话、错误、依赖）；业务时间线（分阶段时延、待确认任务、定位与录音）；应用与中间件（JVM、池、Outbox、Kafka、DB）；容量容灾（增长、WAL、备份、复制、恢复演练）。标注部署与故障事件，支持按 trace 跳转安全日志。

告警包含指标、阈值、持续时间、受影响环境、负责人、处置链接与开始时间；禁止包含手机号、地址或完整事件payload。配置分组、抑制和恢复通知；维护窗口可抑制重复通知但保留SLI记录。每次P1明确“确认→定位→降级/恢复→对账→复盘”，人工处置不得清空队列或共享数据库。

候选可用率99.95%对应错误比例预算0.0005，可使用短长窗共同超过预算的burn-rate策略：例如5分钟和1小时均>14.4倍预算触发快速告警，30分钟和6小时均>6倍触发慢速告警，并加样本数/黑盒条件。阈值须通过历史流量回放校准。

## 5. 性能测试与指标验收

采用[数据库容量模型](数据库硬件容量规划.md)：日50,000警单、10,000警力每15秒上报、短峰50单/秒。明确API读写比例、每单事件/回执数及客户端重试，使用开放到达率或校正协调遗漏的压测方式，防止系统变慢后客户端自限速导致虚假低延迟。

执行顺序：空库功能正确性→保留规模数据预加载→预热→稳态60分钟→15分钟突发→故障接管/N-1→积压追平→24小时稳定性。每组记录提交SHA、JDK/DB/中间件版本、机器与磁盘规格、配置、样本数、吞吐、错误率、P50/P95/P99、CPU/IO、WAL及GC；无压测证据不得将本文目标改为“达标”。

积压追平按 `净追平速度=消费处理速率-实时到达速率` 计算，要求大于0并能在批准窗口内恢复。当前Outbox单调度器理论约20事件/秒，而示例短峰50单/秒×15事件=750事件/秒，15分钟可积压约657,000条；目标设计须达到峰值持续处理并留恢复余量。吞吐不靠忽略失败事件或放宽幂等实现。

指标验收包括：告警注入与恢复通知、断采检测、直方图边界检查、跨实例聚合核对、日志隐私检查、监控开销、实际接收人确认。真实通话/录音与终端环节由获授权的测试线路验收，不对生产紧急呼叫制造负载。

## 6. 实施阶段

第一阶段：接入应用/DB基础指标、请求trace与安全错误计数，修复评审中正确性问题，建立Outbox和超时扫描告警。第二阶段：接入真实Kafka、CTI、终端、录音与定位指标，完成业务对账和故障注入。第三阶段：容量/N-1/恢复演练，冻结SLO、阈值、保留期、值班责任和运行手册。
